# sample —— 十二颗 IMU 的扫描调度

## 职责

按固定节拍把十二颗 IMU 的数据收上来：

- 每 5ms 触发一轮扫描，逐颗选通、读 FIFO、解析成样本
- 给每一批数据打统一时间戳
- 把原始批次塞进队列，交给 `fusion`
- 统计丢帧、FIFO 溢出、单颗通信失败

这一层是全系统的时序中心。它慢一点，`fusion` 就没有数据可算；它乱一点，姿态就会跟着抖。

## 依赖

- `drivers/qmi8658a`：读 FIFO、读温度
- `board`：SPI 总线、74HC154 片选、`esp_timer` 初始化
- FreeRTOS：任务、队列、通知

不依赖 `fusion` 和 `io`，数据进了队列就不管了。

## 对外接口

```c
// 建队列、起 T1 任务
esp_err_t sample_start(void);

// 取一批原始样本，供 fusion 调用。超时毫秒数
bool sample_fetch(raw_batch_t *out, uint32_t timeout_ms);

// 丢帧与错误统计
sample_stats_t sample_get_stats(void);
void sample_reset_stats(void);
```

`sample_fetch` 是阻塞式取队列，`fusion` 在里面等，避免忙等空转。

## 验收（P0）

- 连续跑 10 分钟，每颗 IMU 的样本总数与标称 ODR 的偏差小于 1%
- 丢帧计数为 0，或在出现时能定位到是哪颗、哪一轮
- 单颗通信失败时其余十一颗照常出数据，失败计数加一
- 每轮扫描耗时打印出来，稳定在 1ms 以内

第一条验证时序，第三条验证容错，两条都过才算调度站住了。

## 当前实现架构（尚未实现）

### 简介

一个 5ms 的定时器把采集任务叫醒，任务依次给 12 颗 IMU 上电选通、读走它们 FIFO 里攒的样本，凑成一批塞进队列。谁读失败了就跳过谁，不耽误别的。

### 为什么用 esp_timer 而不是 vTaskDelayUntil

`vTaskDelayUntil` 是相对自身唤醒时刻算周期的，一旦某轮超时，后面的节拍会跟着顺延，误差累积。

`esp_timer` 走的是硬件定时器，回调里只做一件事——`xTaskNotifyGive` 把采集任务叫醒，然后立刻返回。节拍由硬件守，不受任务调度影响。任务被抢占造成的延迟不会传递到下一个周期。

### 采集任务

T1 跑在 core1，优先级 18。一轮的动作固定：

| 步骤 | 内容 |
|---|---|
| 1 | 等通知，收到就记下 `esp_timer` 微秒数 |
| 2 | 循环 12 颗，每颗：选通 → 读样本数 → 读 FIFO → 解析 |
| 3 | 把整批写入队列，顺带填上时间戳和每颗的样本数 |
| 4 | 清空本轮错误计数，回到第 1 步 |

一轮的总耗时要打点记录，超阈值就记日志。正常应在 700 到 800µs。

### 批数据结构

```c
#define IMU_COUNT      12
#define MAX_BATCH_SAMP 8

typedef struct {
    uint8_t  count;
    bool     valid;
    int16_t  acc[MAX_BATCH_SAMP][3];
    int16_t  gyro[MAX_BATCH_SAMP][3];
} imu_slot_t;

typedef struct {
    uint32_t    ts_us;
    imu_slot_t  imu[IMU_COUNT];
} raw_batch_t;
```

按批而不是按颗入队，是因为 `fusion` 需要同一时刻的十二颗一起去算相对姿态。分成十二个队列项反而要在下游重新对齐。

`MAX_BATCH_SAMP` 取 8，够装 896.8Hz 下 5ms 的 4 到 5 个样本，还留了翻倍余量。

### 时间戳

一批只有一个时间戳，取本轮开始时 `esp_timer` 的微秒值。

不逐颗打时间戳，是因为颗与颗之间的采样相位本来就对不齐，逐颗打只会制造一种「很精确」的假象。批级时间戳配合批内均匀假设，对 10ms 的延迟目标足够。

### 队列与丢帧

队列深度 4，够下游抖动一两轮。满了不阻塞，直接丢最旧的一批并计数。

采集任务优先级最高，不能因为队列满就挂起——那样会连带拖垮节拍。

丢帧计数分两个口径：

| 计数 | 含义 |
|---|---|
| `drop_batch` | 整批被丢，下游来不及处理 |
| `drop_imu` | 单颗读失败或 FIFO 溢出，十一颗照常 |

两个数都进 `sample_get_stats()`，上位机能取到。丢帧本身不可怕，可怕的是丢了却不知道。

### 单颗失败的处理

某颗读不出来时，把它的 `valid` 置 false，其余照常。下游 `fusion` 遇到 `valid == false` 就沿用上一轮的姿态，不重算。

失败原因分三类，用不同计数：

| 情况 | 计数 |
|---|---|
| FIFO 里没数据 | 正常，不算错 |
| 样本数超过 `MAX_BATCH_SAMP` | 记 `overrun`，说明读得太慢 |
| SPI 通信没应答 | 记 `comm_err`，说明那颗可能掉了 |

### 片选切换

74HC154 的地址线由四个 GPIO 直接驱动，切换后没有显式延时，紧接着就是 SPI 事务。

GPIO 写入到 SPI 第一个时钟沿之间的函数调用开销已经覆盖了译码器的传播延迟。如果实测出现首字节读错，再在切换后补一个几微秒的忙等。

### 温度与磁力计

不进 T1 主循环。温度 1 秒读一次，磁力计 100Hz 读一次，各自由低优先级任务做，读到的值挂在一个共享结构里，`fusion` 和 `io` 按需取。

把它们从主循环里拆出去，是因为它们都不需要 5ms 的节拍，混进来只会让 T1 变长。
